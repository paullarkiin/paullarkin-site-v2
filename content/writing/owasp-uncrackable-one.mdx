The methods in `sg.vantagepoint.a.c` look for a `su` binary on the device path, `test-keys` in `Build.TAGS`, and known root-related files. These are simple indicators rather than proof that a device is rooted, but any one of them is enough to stop the app.

### Decoding the secret with static analysis

At this point everything needed to recover the secret is inside the APK. The key is `8d127684cbc37c17616d806cf50473cc`, and the ciphertext is `5UJiFctbmgbDoLXmpL12mkno8HT4Lv8dlat8FxR2GOc=`. The helper class uses AES with ECB mode and PKCS#7 padding, which I reproduced in Python:

```python
import base64
from Crypto.Cipher import AES
from Crypto.Util.Padding import unpad

key_hex = "8d127684cbc37c17616d806cf50473cc"
encoded = "5UJiFctbmgbDoLXmpL12mkno8HT4Lv8dlat8FxR2GOc="

key = bytes.fromhex(key_hex)
ciphertext = base64.b64decode(encoded)
cipher = AES.new(key, AES.MODE_ECB)

plaintext_padded = cipher.decrypt(ciphertext)
print("Raw decrypted:", plaintext_padded)

plaintext = unpad(plaintext_padded, AES.block_size)
print("Plaintext:", plaintext.decode())
```

Running the script produces:

```text
$ python3 solve.py
Raw decrypted: b'I want to believe\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f'
Plaintext: I want to believe
```

The repeated `\x0f` bytes are the PKCS#7 padding. After removing them, the secret is **`I want to believe`**.

### Takeaway

The challenge demonstrates why secrets should not rely on client-side protection alone. The key, ciphertext, and decryption logic are all stored inside the APK, so static analysis is enough to recover the plaintext without modifying or instrumenting the running app.
